# Agent Note: Rust JSON-RPC 启动与追加序列化

Status: implemented

[English](2026-08-25-rust-jsonrpc-startup-and-append-serialization.md) | 中文

## 问题

stdio JSON-RPC 服务器的传输层一旦启动，外部就能访问它。此时 Loader 配置中的后续同级项可能仍在激活，包括回放所选的适配器。SDK 客户端若立即发送 `initialize`，就可能观察到不完整的插件树，并在已配置适配器出现之前促使服务器安装在线 DeepSeek 回退适配器。

Rust 执行器线程还允许两个独立的会话追加调用方发生重叠：其中一个调用方为提交前发布而暂时释放会话数据锁时，另一个调用方可以进入。若把这种重叠当作同步重入，就会拒绝本应有序执行的工作，例如会话标题追加与请求头构造发生竞争。真正的同线程嵌套追加必须继续保持无效，因为它会递归进入同一项接纳事务。

## 决策

进程 launcher 通过 `deferred_plugin()` 注册 `seekdeep-sdk-jsonrpc-server`。其请求处理器在单向就绪锁存器后排队，直到 `seekdeep-jsonrpc-agent` 完成整个 app-boot 与 Loader 完全停稳事务，随后 runner 调用 `mark_ready()`。排队帧保持传输顺序。程序内嵌入与显式流测试继续使用立即就绪的 `plugin()` 和 `apply_with_runtime()` API。

SDK DeepSeek 回退路径使用空配置对象挂载提供方插件，绝不传入 JSON `null`；当没有已配置适配器拥有 `deepseek-official` 时，普通默认配置路径仍然有效。

每个 `Session` 都拥有一个覆盖准备、提交与发布阶段的可重入追加门。其他执行器线程会在此门处等待，并在当前追加结束后取得下一个序号。同线程同步嵌套调用会重新取得该门、观察到现有接纳标记，并返回 `ReentrantAppend`；因此，该 guard 会序列化任务交错，同时不削弱递归不变量。

## 验证

SDK 服务器套件证明：排队的 `initialize` 请求无法在就绪前结算，并会在锁存器打开后完成。已编译 JSON-RPC 示例通过真实 Loader、SDK 子进程、工具、子 agent 和 JSONL 持久化回放全部四个已检入 SDK 场景。在线 loopback DeepSeek 矩阵钉住三种 max-token 映射模式、精确的面向模型工具、输出上限、Zstandard 日志、stdout 纯净性与无效环境诊断。Rust 极简客户端驱动独立的持久工具组合，并证明最终 stdout 与所拥有进程的清理行为。

## 曾考虑的替代方案

**把服务器配置项移到每份配置末尾。** 不予采用，因为配置来自外部且顺序由用户编写；就绪属于 launcher 不变量，不应成为每个 profile 都要记住的约定。

**让服务器在启动后重试回退适配器选择。** 不予采用，因为第一次 `initialize` 仍会观察并修改不完整的组合。所选应用就绪之前，任何协议操作都不得开始。

**把会话追加转换为异步 API。** 不予采用，因为追加是一项同步且使用广泛的提交操作，而源事件循环本就会序列化独立调用方。进程内门可以保留该语义，无需把异步取消与所有权扩散到每个生产方。

## 后果

立即发起请求的 SDK 客户端无法再与已配置适配器或其他后加载 Loader 配置项竞争。独立 Rust 任务会按一条连续序列提交会话事件，而递归监听器错误仍会在精确的追加边界失败。进程 launcher 必须在成功启动后显式打开延迟服务器；若 launcher 遗漏此操作，请求会保持等待，而不会暴露不完整状态。
