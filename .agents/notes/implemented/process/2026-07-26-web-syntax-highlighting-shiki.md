# Agent Note: Web client syntax highlighting — synchronous fine-grained shiki

Status: implemented

English | [中文](2026-07-26-web-syntax-highlighting-shiki.zh.md)

> Scope: the web client's one syntax-highlighting system — the dependency ruling, the singleton shape, the token-sheet contract, and the consuming surfaces. Fifth PR of the Code Mode UI stack; the [chat sub-call rows note](../feature/2026-07-26-code-mode-chat-subcall-rows.md) shipped the `run_code` program body this exists to make readable. Styling ground rules are owned by [the web styling ruling](2026-07-19-web-styling-system.md).

## Problem

The client rendered every code surface — markdown fences in assistant prose, the `run_code` program body, the details panel's args — as flat monospace text. The stack's primary payload is model-written TypeScript; unhighlighted programs are measurably harder to scan, and the repo already ships shiki-highlighted code on its VitePress site, so the web app was the one code-rendering surface without it.

## Decision

**Shiki in its synchronous fine-grained form, as one `ui-primitives` singleton, themed exclusively through CSS custom properties.**

- **Dependency**: `shiki/core` + `@shikijs/langs`, composed via `createHighlighterCoreSync` with `createJavaScriptRegexEngine({ forgiving: true })` — no oniguruma WASM, no async boot initialization, bundle-friendly. The boot set is `typescript` (embeds JS), `shellscript`, and `json`; 23 read-card grammars sit behind the closed lazy table. Anything outside that combined allowlist falls back to a geometry-identical plain block, never an error. Prior art: the VitePress site already renders all documentation code through Shiki, and TextMate grammars materially beat regex highlighters on TypeScript — the payload that matters here.
- **Singleton and ownership**: compiled Rust/WASM ([browser_highlight.rs](../../../../crates/client-ui-primitives/src/browser_highlight.rs)) owns aliases, boot/lazy admission, one-shot load requests, load-count publication, subscriptions, fallback behavior, HTML dispatch, per-line token shaping, and trailing-line normalization. The pure-library ESM package generated by [`xtask`](../../../../xtask/src/main.rs) supplies a thin Shiki capability: it constructs the one `HighlighterCore`, embeds the three boot grammars, and contains the 23 syntax-level dynamic import thunks, but makes no Harness policy decision. Rust schedules deferred warmup so the ~120-175ms engine construction stays off the finalized-stream render path. Assistant-authored labels such as `constructor` miss in Rust's closed alias table rather than resolving through an object prototype. The compiled `CodeBlock` ([browser_code_block.rs](../../../../crates/client-ui-primitives/src/browser_code_block.rs)) owns highlighted and plain arms; its highlighted arm injects Shiki's static span tree through `dangerouslySetInnerHTML`, the dependency's documented consumption path, with no user HTML, scripts, or handlers.
- **Theming**: shiki's `createCssVariablesTheme` routes every token color through `--shiki-*` custom properties; the VALUES live in a new `ui-theme/styles/shiki.css` token sheet (light on `:root`, dark on `body[data-ds-dark-theme]` — the same cascade as every other sheet), imported by the shell's `base.css` chain. Component CSS stays tokens-only; no literal color ever enters JS or component sheets. Background/foreground alias the existing markdown code-block tokens so highlighted and plain blocks agree.
- **Surfaces**: markdown fences (`MarkdownText`'s `pre` component routes single-string fences through `CodeBlock`), the `run_code` expanded program body (`lang="typescript"`), the details panel's Input args (`lang="json"`), and the line-numbered `ReadBlock` through the same per-line tokenizer. Tool output is never syntax-highlighted — it is arbitrary text, and guessing a grammar would mis-highlight more than it helps; a bash card's output carries only the color its own ANSI sequences declare, through [the terminal card](../feature/2026-07-28-web-terminal-card.md).

## Alternatives considered

**`rehype-highlight`/lowlight.** Runner-up: naturally sync and ~⅓ the bundle, but regex-grammar fidelity on TypeScript is visibly worse, and the repo would then run two highlighter systems (site: shiki, app: highlight.js) with two theming vocabularies.

**Full `shiki` bundle or the oniguruma WASM engine.** Rejected: the full bundle ships every grammar/theme; WASM needs async loading the sync client boot deliberately avoids. The fine-grained core with three grammars keeps the cost proportional to actual use.

**Highlight in a worker / async.** Rejected: the payloads are small (programs, fences, args); the synchronous JS engine tokenizes them in microseconds, and async introduces a flash-of-unhighlighted-code plus render-machinery churn for no measured need.

## Consequences

One Rust-owned policy and one Shiki singleton serve every consumer. The bundle grows by Shiki core plus the three boot grammars; each lazy grammar is paid only after first use. Token colors remain on the `--shiki-*` sheet. Pinned source specs, live WASM policy/component tests, the optimized ESM package test, and a real Shiki-to-WASM smoke pin aliasing, token/HTML output, lazy notification, fallback, copying, and block chrome. The remaining Markdown renderer and full package-index rows stay independently pending until their complete assembled paths are compiled.
